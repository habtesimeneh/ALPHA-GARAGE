# Security Architecture & Design Specification
## Garage Management System with Secure Data Storage and Auditing

**System:** AutoPro Garage Management System (Group 1)  
**Security Standard:** OWASP Top 10 (2021/2025 compliant), NIST SP 800-63B Authentication Guidelines  
**Classification:** Confidential Enterprise Information System  

---

## 1. Executive Security Architecture

The AutoPro Garage Management System is architected according to the **Defense-in-Depth** principle. Security controls are enforced at every architectural tier:

```
[ Client Browser ]
        │  HTTPS / Strict-Transport-Security (HSTS)
        ▼
[ HTTP Security Boundary ]
        │  CSP, X-Frame-Options: SAMEORIGIN, X-Content-Type-Options: nosniff, SameSite Cookies
        ▼
[ Application Layer (PHP 8.x) ]
        │  • Session Verification (Regeneration, Idle Timeout, IP Fingerprint)
        │  • CSRF Token Validation on all State-Changing Requests
        │  • Server-Side RBAC Enforcement (Role/Permission Matrix)
        │  • Input Validation & Sanitization (Strict Regex, Types)
        │  • Output Escaping (Context-Aware htmlspecialchars)
        ▼
[ Cryptographic Services Layer ]
        │  • AES-256-GCM Authenticated Encryption
        │  • Blind Indexing (HMAC-SHA256) for Exact-Match Lookups
        │  • Key Isolation in storage/private/ (Denied via Web Server)
        ▼
[ Database Layer (MySQL / MariaDB InnoDB) ]
        │  • 100% Parameterized Prepared Statements (Zero SQL Concatenation)
        │  • Append-Only Triggers on Forensic Audit Log (UPDATE/DELETE Denied)
        │  • Atomic Serialized Hash Chaining (SHA-256 HMAC Head Mutex)
        ▼
[ Storage & OS Layer ]
        • Directory Permissions (Read-Only Code, Non-Executable Storage)
```

## 2. Authentication & Credential Management

### 2.1 Password Hashing & Verification
- **Algorithm:** `PASSWORD_BCRYPT` with cost factor 12 (or Argon2id where natively compiled in PHP 8.x).
- **Salting:** Cryptographically secure, unique 128-bit random salt automatically generated by `password_hash()`.
- **Timing Defense:** Verification executed via `password_verify()`, preventing timing attacks.
- **Rehashing:** `password_needs_rehash()` checked during every successful login to automatically migrate hashes when algorithm parameters are upgraded.

### 2.2 Password Complexity Policy
All user passwords must satisfy NIST SP 800-63B memorized secret guidelines:
- Minimum length: 8 characters (maximum 72 bytes due to Bcrypt boundary).
- At least one uppercase Latin letter (`A-Z`).
- At least one lowercase Latin letter (`a-z`).
- At least one numeric digit (`0-9`).
- At least one non-alphanumeric special symbol (`!@#$%^&*()_+-=[]{}|;:,.<>?`).

### 2.3 Brute-Force & Credential Stuffing Mitigation
Two independent layers of rate limiting are enforced via `login_attempts`:
1. **Target Account Lockout:**
   - Maximum 5 consecutive failed attempts per username.
   - Once exceeded, account status is set to `locked_until = NOW() + 15 minutes`.
   - Admin alert notification is logged.
2. **Client IP Rate Limiting:**
   - Maximum 10 failed attempts per originating IPv4/IPv6 address within any rolling 15-minute window.
   - Further authentication attempts from that IP receive HTTP 429 Too Many Requests.
3. **Generic Error Responses:**
   - Failed logins return `"Invalid username or password"`, preventing account enumeration.

### 2.4 Public Form Abuse Protection (Phase 1)
`public/register.php` and `public/contact.php` apply server-side throttling before any validation or persistence:
- **Registration:** maximum 5 POST attempts per IP per 15-minute window.
- **Contact inquiries:** maximum 5 POST attempts per IP per 10-minute window.
- **Mechanism:** `RateLimiter` (`app/services/RateLimiter.php`) stores a hashed `action|client_ip` key in `storage/rate_limits/`, guarded by `flock(LOCK_EX)`. Counters contain no personal data and use fixed windows.
- **Denied requests:** HTTP `429 Too Many Requests` with a `Retry-After` header and a generic user-facing message. Validation and persistence are skipped.
- **Honeypot:** both forms include a visually hidden `hp_website` field. Submissions that fill it are acknowledged without creating a record (contact) or an account (registration).
- **Fail-open:** if the rate-limit storage is unavailable the failure is logged and requests are allowed, so a storage problem cannot take public forms offline.
- CSRF verification still runs globally before these checks, and normal submissions are unaffected.

### 2.5 Session Security Lifecycle
Native PHP session management is fortified with hardened configuration directives:

| Session Directive | Configured Value | Security Purpose |
|---|---|---|
| `session.cookie_httponly` | `1` (true) | Disallows JavaScript access (`document.cookie`), preventing XSS session theft |
| `session.cookie_secure` | Auto (`1` on HTTPS) | Prevents transmission over unencrypted HTTP |
| `session.cookie_samesite` | `Lax` | Mitigates Cross-Site Request Forgery (CSRF) on navigation |
| `session.use_strict_mode`| `1` (true) | Prevents session adoption / fixation attacks |
| `session.use_only_cookies`| `1` (true) | Forbids session IDs passed in URL query parameters |

- **Session Regeneration:** `session_regenerate_id(true)` is executed immediately upon successful authentication, invalidating the pre-login session ID.
- **Inactivity Timeout:** Idle sessions expire after **30 minutes** of inactivity (`SESSION_IDLE_TIMEOUT`).
- **Absolute Lifetime:** Sessions are forcibly terminated after **8 hours** (`SESSION_MAX_LIFETIME`), requiring re-authentication.
- **Device & IP Binding:** Sessions record client IP and User-Agent signature. A sudden change in client characteristics invalidates the session.

### 2.5 Password Recovery Workflow
- Self-service recovery generates a 64-character hex cryptographically secure token (`random_bytes(32)`).
- The raw token is delivered to the user; **only the SHA-256 hash** is persisted in `password_resets`.
- Tokens expire after **60 minutes** and are strictly single-use (`used_at` flag).

### 3.3 Server-Side Enforcement (Defense Against IDOR)
- **Zero Frontend Reliance:** Hiding navigation links in UI is treated merely as UX convenience. Every single backend endpoint enforces authorization via:
  ```php
  require_permission('inventory.manage');
  ```
- **Horizontal Access Control (Mechanics):** When a mechanic accesses job cards, queries restrict scope:
  ```php
  if (!can('jobs.view_all') && can('jobs.view_assigned')) {
      $sql .= " AND j.mechanic_id = ?";
      $params[] = current_user()['mechanic_id'];
  }
  ```
  Attempting to load a job belonging to another mechanic results in HTTP 403 Forbidden.

## 4. Cryptographic Storage & Key Management

### 4.1 Authenticated Symmetric Encryption (`CryptoService.php`)
For sensitive settings and confidential data, authenticated symmetric encryption is used:
- **Cipher:** `AES-256-GCM` (Galois/Counter Mode).
- **Properties:** Confers both **confidentiality** and **ciphertext integrity** (authenticity).
- **Initialization Vector (IV):** 96-bit (12 bytes) cryptographically secure pseudorandom IV (`random_bytes(12)`). IVs are **never reused**.
- **Authentication Tag:** 128-bit (16 bytes) GCM auth tag generated on encryption and validated during decryption.
- **Tamper Detection:** Modifying even 1 bit of the stored ciphertext or tag causes decryption to immediately fail with a cryptographic exception, preventing bit-flipping attacks.
- **Serialization Format:**
  ```
  v1:<base64(iv)>:<base64(auth_tag)>:<base64(ciphertext)>
  ```

### 4.2 Blind Indexing for Exact-Match Search
To search sensitive fields without decrypting the entire database into memory:
- A cryptographic hash digest is computed:
  ```
  blind_index = HMAC-SHA256(plaintext, blind_index_key)
  ```
- Fast indexed SQL queries execute:
  ```sql
  SELECT * FROM customers WHERE phone_blind_index = ?;
  ```
- The master key and blind index key are cryptographically derived from the root secret using HKDF (`hash_hkdf`).

### 4.3 Key Storage & Isolation
- **Primary Source:** Environment variable `GMS_ENCRYPTION_KEY` (32 bytes / 64 hex characters).
- **Fallback File:** `storage/private/app.key` generated on setup.
- **Web Server Protection:** `storage/private/.htaccess` enforces:
  ```apache
  Require all denied
  ```
  Preventing any web client from downloading the key file directly.

## 5. Web Application Vulnerability Mitigations (OWASP Top 10)

### 5.1 SQL Injection Prevention
- **Strict Invariant:** Zero dynamic SQL string concatenation.
- **Implementation:** 100% of database interactions execute through `Database::run()`, `Database::one()`, `Database::all()`, `Database::insert()`, and `Database::value()` using PDO prepared statements with bound parameters.
- **Identifier Whitelisting:** Any dynamic column or sort direction is validated against a strict internal whitelist before being interpolated.

### 5.2 Cross-Site Scripting (XSS) Prevention
- **Output Escaping:** All dynamic data rendered into HTML documents is passed through the context-aware escaping helper:
  ```php
  function e(?string $v): string {
      return htmlspecialchars((string)$v, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8');
  }
  ```
- **Context Awareness:** Attributes, URLs, and JSON data use specialized encoding (`json_encode()`, `urlencode()`).

### 5.3 Cross-Site Request Forgery (CSRF) Prevention
- **Token Mechanism:** Cryptographically random 256-bit token generated per session (`random_bytes(32)`).
- **Form Injection:** Embedded in all HTML forms via `<?= csrf_field() ?>`.
- **Enforcement:** Every `POST` request is verified in `app/bootstrap.php` via `verify_csrf()`. Mismatched, missing, or expired tokens abort with HTTP 419 and are recorded in the audit log.
- **AJAX Support:** Requests may supply the token in the `X-CSRF-Token` request header instead of the `_csrf` form field.

### 5.4 Content Security Policy (CSP) & HTTP Headers
The application injects these browser defensive headers on every HTTP response (verified in `app/bootstrap.php`):
```http
Content-Security-Policy: default-src 'self'; img-src 'self' data: https://images.unsplash.com; style-src 'self'; script-src 'self'; form-action 'self'; frame-ancestors 'none'; base-uri 'self'
X-Frame-Options: DENY
X-Content-Type-Options: nosniff
Referrer-Policy: same-origin
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

### 5.5 Insecure Direct Object References (IDOR)
- All record IDs in URLs (`?id=42`) undergo server-side entity validation.
- Records check tenant/ownership conditions and user role permissions prior to rendering or mutation.

## 6. Audit Log Integrity & Anti-Tamper Guarantees

### 6.1 Secret Redaction
Before any state change is written to `audit_logs`, the payload is sanitized through a redaction filter:
```php
$sensitiveKeys = ['password', 'password_hash', 'password_confirm', 'token', 'csrf_token', 'secret', 'card_number'];
```
Values associated with these keys are replaced with `"[REDACTED]"`, ensuring passwords and session tokens are never leaked into forensic logs.

### 6.2 Forward Cryptographic Hash Chaining
Every record in `audit_logs` contains:
- `prev_hash`: SHA-256 hash of the preceding audit record.
- `record_hash`: SHA-256 HMAC of `(prev_hash + id + event_time + user_id + action + table_name + record_id + old_value + new_value)`.
- If an attacker tampers with any historic row, every subsequent hash in the chain becomes mathematically invalid.

### 6.3 Database Engine Immutability Triggers
MySQL/MariaDB triggers block any modification or deletion of audit logs:
```sql
CREATE TRIGGER trg_audit_no_update BEFORE UPDATE ON audit_logs
FOR EACH ROW SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'audit_logs is append-only: updates forbidden';

CREATE TRIGGER trg_audit_no_delete BEFORE DELETE ON audit_logs
FOR EACH ROW SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'audit_logs is append-only: deletes forbidden';
```

## 7. Security Incident Response & Verification

1. **Tamper Verification:** Administrators can trigger `AuditLogger::verifyChain()` from the UI or CLI to mathematically check the integrity of every audit entry.
2. **Account Recovery:** In case of administrator lockout, CLI utilities allow resetting credentials directly on the secure server terminal.
3. **Automated Regression Suite:** The security test suite in `tests/run_tests.php` validates password complexity, rate-limiting, CSRF blocking, RBAC segregation, cryptographic encryption, and tamper detection on every release.
